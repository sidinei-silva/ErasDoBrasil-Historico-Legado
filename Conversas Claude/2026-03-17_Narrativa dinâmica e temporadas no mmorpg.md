**O MODELO É SIMPLES: TUDO PERTENCE A UMA ZONA.**

Cada entidade no jogo (player, NPC, mob, recurso) tem um campo `zoneID` que diz onde ela está. A zona é o nó do grafo. O servidor mantém em memória um mapa de zonas, e cada zona tem listas do que está dentro dela.

Conceitualmente em Go, pensa assim:

```
Zone {
    ID
    Name
    RegionID
    LevelRange (min, max)
    Terrain
    Connections []ZoneConnection  // saídas para outras zonas
    
    // Tudo que está DENTRO desta zona agora:
    Players   []PlayerID
    NPCs      []NPCID
    Mobs      []MobID
    Resources []ResourceNode
}
```

Quando o player se move da Vila pra Floresta, o servidor remove o playerID da lista de Players da Vila e adiciona na lista de Players da Floresta. Mesma coisa pra NPCs que seguem rotina e mobs que migram.

---

**ENCONTROS: NÃO PRECISA DE COLISÃO FÍSICA.**

Num MUD, não existe posição X,Y dentro da zona. A zona é um espaço abstrato. "Estar na Floresta do Norte" significa que você está no mesmo espaço que todos os outros que também estão na Floresta do Norte. Isso simplifica enormemente o problema de encontros.

**Player encontra NPC:** Quando o player entra numa zona, o servidor verifica quais NPCs estão nessa zona. O cliente mostra: "Você vê o Ferreiro Tomás trabalhando na forja." O player pode interagir com qualquer NPC presente na zona. Não precisa "andar até ele" — está na mesma zona, pode falar.

**Player encontra Mob:** Mesma lógica. O player entra na zona, o servidor verifica quais mobs estão lá. Mas combate não é automático — o player escolhe engajar ou não. "Você avista 2 Lobos e 1 Espírito Menor na Floresta." O player pode atacar, ignorar, ou tentar evitar (teste de Astúcia). Se o mob é agressivo (tipo definido no template), ele pode iniciar combate automaticamente após X segundos se o player não sair.

**Player encontra Player:** O player entra na zona e vê a lista de outros players presentes. "Também estão aqui: Kaira (Guerreiro Tribal Nv.3), Domingos (Missionário Nv.2)." Sem PvP no MVP, eles só coexistem — podem trocar itens, conversar, ou competir por mobs e recursos.

**NPC encontra NPC:** No game loop, o NPCManager processa movimento de NPCs por rotina. Quando dois NPCs estão na mesma zona, o sistema de Fofoca pode trocar informação entre eles. Isso já está definido no Cap. 8 — +1 conhecimento mútuo, troca de knowledgeBase.

**NPC encontra Mob:** Geralmente NPCs ignoram mobs e vice-versa (simplifica o MVP). Se quiser no futuro, NPCs podem reagir a mobs agressivos (fugir, lutar, pedir ajuda), mas isso é complexidade de Temporada 2+.

**Mob encontra Mob:** Não interagem entre si no MVP. No futuro, se implementar ecossistema (Opção B dos Inimigos Evolutivos), lobos podem caçar presas, etc. Mas isso é muito longe.

---

**RECURSOS: SÃO FIXTURES DA ZONA, NÃO ENTIDADES MÓVEIS.**

Recursos (ervas, minérios, madeira) não se movem. São nós de coleta fixos dentro da zona. Cada zona tem uma lista de `ResourceNode`:

```
ResourceNode {
    ID
    Type          // "erva_lua", "minerio_ferro", etc.
    MaxQuantity   // quanto regenera no máximo
    CurrentQty    // quanto tem agora
    RegenRate     // quanto regenera por período do dia
    RequiredSkill // proficiência necessária
    RequiredCD    // classe de dificuldade do teste
}
```

Quando o player coleta, `CurrentQty` diminui. A cada período do dia, o game loop regenera recursos conforme `RegenRate`. Se muitos players coletam na mesma zona, os recursos esgotam — isso distribui players naturalmente pelas zonas e cria economia de escassez.

---

**MOVIMENTO ENTRE ZONAS: É UMA AÇÃO COM DURAÇÃO.**

Quando o player decide ir da Vila pra Floresta, não é instantâneo. O servidor:

1. Verifica se a conexão existe (Vila → Floresta está no grafo).
2. Calcula o tempo de viagem (definido na conexão, ex: 10 minutos reais).
3. Coloca o player em estado "viajando" — ele sai da zona de origem mas não chegou na destino.
4. Após o tempo, o player chega na zona destino e é adicionado à lista de Players dela.

Durante a viagem, o servidor pode disparar eventos aleatórios de encontro (emboscada, NPC viajante, recurso no caminho). Isso está definido no Cap. 5 §5.2.

---

**O FLUXO NO GAME LOOP:**

A cada ciclo do game loop sequencial (que você já definiu no ADR-005):

```
WorldManager:
  - Avança relógio do jogo
  - Regenera recursos por zona
  - Processa viagens em andamento (player chegou? → muda de zona)

NPCManager:
  - Para cada NPC: verifica rotina do período
  - Se precisa mudar de zona → move (remove da zona antiga, adiciona na nova)
  - Se está na mesma zona que outro NPC → troca Fofoca

MobManager (parte do NPCManager ou separado):
  - Verifica se mob evoluiu → se sim, migra
  - Verifica se mob agressivo está na zona com player → pode iniciar combate
  - Spawn de mobs novos em zonas com população abaixo do cap

QuestManager:
  - Verifica prazos de quests
  - Verifica se player completou objetivos na zona atual

CombatManager:
  - Resolve combates ativos (turno a turno, D20)
```

**RESPOSTA DIRETA PRA SUAS PERGUNTAS:**

"Como vou dizer player X está aqui?" → Campo `zoneID` no player. O servidor sabe quem está em cada zona pela lista `zone.Players`.

"Como NPC está ali?" → Campo `zoneID` no NPC. Muda conforme rotina processada pelo NPCManager.

"Monstros e recursos?" → Mobs têm `zoneID` e se movem (migração). Recursos são fixos na zona com quantidade que regenera.

"Encontro entre entidades?" → Estar na mesma zona = estar "junto". O servidor verifica as listas de cada zona pra saber quem está com quem. Não existe posição X,Y — é tudo por zona.

**O cliente web É o cliente desktop E o cliente mobile.**

Num MUD moderno, o cliente é leve — recebe JSON via WebSocket e renderiza texto + painéis de UI. Não tem 3D, não tem sprites pesados, não tem engine gráfica. É basicamente uma interface web rica. Isso significa que um único cliente web bem feito roda em qualquer lugar.

**Desktop:** O jogador abre o navegador e joga. Zero instalação, como já está no Game Pitch. Se quiser uma "sensação de app desktop", envolve o cliente web num Electron ou Tauri e distribui como executável. Mas isso é cosmético — o jogo é o mesmo.

**Mobile:** O mesmo cliente web responsivo funciona no navegador mobile. Se quiser app nativa, envolve num WebView (Capacitor, TWA no Android). De novo, cosmético.

**A recomendação é: faça UM cliente web responsivo e esqueça multi-plataforma por agora.** As razões são:

Você é dev solo com 6h/semana. Manter 3 clientes (web, desktop nativo, mobile nativo) é manter 3 projetos. Manter 1 cliente web que funciona nos 3 é manter 1 projeto.

MUD moderno é texto + UI. Não precisa de acesso a GPU, não precisa de controles nativos de toque especiais, não precisa de notificações push complexas. Tudo que o jogo precisa (WebSocket, renderização de HTML/CSS, input de texto) funciona perfeitamente no browser.

Jogos que são referência pra você (Fallen London, Torn, Kingdom of Loathing, Melvor Idle) são todos web-first. Alguns têm app mobile mas são literalmente o site envelopado.

---

**Se no futuro quiser mesmo clientes nativos, o caminho seria:**

Para desktop, **Tauri** (Rust + WebView) em vez de Electron. É mais leve, gera executáveis menores, e como o cliente é web, você só envelopa o que já tem. Alternativa: distribuir como PWA (Progressive Web App) — o jogador "instala" do navegador e parece app nativo sem você fazer nada extra.

Para mobile, **PWA** é a primeira opção — funciona no Android e iOS, instala da home screen, funciona offline (se configurar service worker). Se precisar de app store, **Capacitor** (Ionic) envelopa seu site web em app nativo com uma linha de config. Alternativa: **TWA** (Trusted Web Activity) pro Android que é literalmente o Chrome embutido rodando seu site como app.

Para ambos, se quisesse algo realmente nativo sem web, **React Native** ou **Flutter** consumindo a mesma API WebSocket do servidor Go. Mas aí é reescrever toda a UI do zero em outro framework — não faz sentido pro MVP.

---

**A stack que faz sentido pra você:**

| Plataforma | Tecnologia | Esforço |
|-----------|-----------|---------|
| Web (primário) | HTML/CSS/JS vanilla ou React | É o que você já vai fazer |
| Desktop "app" | PWA ou Tauri envelopando o web | ~1 dia de trabalho |
| Mobile "app" | PWA ou Capacitor envelopando o web | ~1 dia de trabalho |

As 3 plataformas consomem o mesmo cliente web. O servidor Go não sabe nem se importa de onde vem a conexão WebSocket — browser, Tauri, Capacitor, tudo é WebSocket com JSON.

**Minha recomendação concreta:** faz o cliente web na Fase 2-3 como está planejado. Quando estiver funcional e jogável, gasta 1 dia configurando PWA (manifest.json + service worker) e você ganha "app" mobile e desktop de graça. Clientes nativos de verdade ficam pra quando tiver audiência que justifique o investimento — e provavelmente nunca vai precisar porque PWA resolve.
